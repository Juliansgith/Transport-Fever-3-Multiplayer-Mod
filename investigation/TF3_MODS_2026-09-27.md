# What third-party TF3 mods tell us -- 2026-09-27 (build 40391)

Before release, the team got nine script mods by "GameWatcher" (GW Big
City, Huge City, Bigger Station Range, Buy Industries, Cheats, Faster Game
Speed, Headquarters Growth Boost, Quality of Life 1.0.0 and 1.1.0, Startup
Fortune), each "made for game build 40391". Their code and READMEs are the
first evidence from a real Transport Fever 3 build. This page says what they
show and which of our assumptions it changes. The mods themselves are not in
the repository; they are not ours to redistribute.

Every finding here is labelled **REPORTED** (see [DAY_ONE.md](../docs/DAY_ONE.md)):
the mods rely on it, or their comments say so, for a pre-release build. It
is stronger than INFERRED, since working code depends on it, but we have not
seen it ourselves, and build 40391 may not be the release build. Release day
confirms each finding or overturns it.

## What changes for us

| our assumption | what the mods show | where it is used |
|---|---|---|
| A mod is TPF2's layout: `mod.lua` with `data()` returning `info`, and `res/...` | `mod.json`, `_content.json` listing every file under `content/`, and `_metadata/modinfo.json` (name, description, authors, tags) | `mod/tpf3mp_1`, both probe mods, `installed_mod` in the launcher |
| Mods live in `<Steam>/userdata/<account>/3493540/local/mods` | Local mods go in `.../3493540/local/staging_area/<mod>_1`, then the player activates them in **Mod Hub**; "a mod that is not activated does nothing" | the install scripts, PLAYING.md |
| Scripts are Lua 5.2, loaded with `require "a.b"` | The game's own scripts are **Teal** (`.tl`, typed Lua). Files load with `ug_require "::/path/file.tl"` (the game's content) or `"<modId>::/path"` (a mod's). A construction script (`.script.lua`) also has plain `require` with a `::/` path. | every Lua file we ship |
| Probes run as `res/config/game_script/<name>.lua` with `update()` in the engine state and `guiUpdate()` in the GUI state | No mod uses a game script. Code that runs every frame is a GUI **react plugin** with `react.onStep`. No mod shows whether game scripts still exist. | both probe mods |
| `api.cmd.sendCommand`, `api.engine.getComponent`, `api.type.ComponentType.*` are TPF2 names to be confirmed | All present, used as in TPF2 | `mod/tpf3mp_1/.../engine.lua` |
| The player's commands are built in native code and reach script only on our replay (the caller-RVA filter, HOOKS.md) | The stock GUI is script (Teal): the speed buttons, the line manager, the game bar, the entity windows. Mods send commands from that GUI with `api.cmd.make*Cmd` and `api.cmd.sendCommand`, the path our replays take. Whether the stock GUI does the same is not shown, but likely. | the capture design, HOOKS.md, PLAN Part 2 |
| Speed and pause need a native hook (PLAN Part 2, Dev A) | The speed row is a script recipe (`game_bar_widgets.GameSpeedControl`) that calls `gameSpeedHelper:getApi().setSpeed`. A mod replaces it. The engine takes any speed, not only 1x to 4x. | `Control::Speed` |

## The mod format

REPORTED, from all nine mods:

- **`mod.json`** at the mod's root: `modId` (`gw_big_city_1`, the folder's
  name), `revision` (an integer), `severityAdd` / `severityRemove`
  (`"None"`, not TPF2's `"NONE"`), `dependencies`, `incompatibilities`,
  `options`, `params`, and three script hooks: `preRunScript`, `runScript`,
  `postRunScript`, each `{ "fileName": "<modId>::/mod.script@runFn" }` or
  `""` for none.
- **`_content.json`**: `{ "archives": null, "files": [...] }`, every file
  under `content/` by its path relative to `content/`.
- **`_metadata/modinfo.json`**: `name`, `summary`, `description`,
  `authors` (`name`, `role: "CREATOR"`), `tags` (`"Script Mod"`), `url`.
  `_metadata/0.png` is the preview image.
- **Scripts.** A `.script.lua` must define a global `data()` that returns
  its table ("function data() not defined" otherwise). A `.tl` file
  returns its table at the top level. The run script's `runFn` takes
  `(captureParams, settings)`, where TPF2's took `(settings)`.
- **Modifiers.** `addModifier("loadConstruction", fn(fileName, data))` and
  `addModifier("loadModule", ...)` work as in TPF2. A construction's
  `updateScript.fileName` and `createTemplateScript.fileName` are
  `"<file>@<function>"`, so a mod can point them at its own script.
- **GUI resources** (`content/gui/.../*.res.lua`, returning `data()`):
  - `type = "react-plugin ::<ExtensionPoint>"`, with `filePath =
    "<modId>::/gui/.../x.script@Recipe"`, `priority` or `order`, and an
    optional `condition` function.
  - `type = "react-replacement-config"`, with `filePath` and `doReplaceFn`.
    The game runs `doReplace(replacementApi)` before any recipe renders
    (`gui/main/bootstrap_game.tl`). Then
    `replacementApi.ReplaceRecipe(original, new)` swaps a recipe for every
    caller, and `react.CallOriginalRecipe` calls the one it replaced.
  - Extension points in use: `GameBarInfoDisplayExtension` (the game bar),
    `TownEowExtensionPoint`, `IndustryEowExtensionPoint` and
    `VehicleEowExtensionPoint` (entity windows).
  - `ug_require` returns the shared module table, so assigning over one of
    its fields (`game_bar_widgets.GameSpeedControl = ...`) replaces it for
    the whole GUI.

## The script API seen

REPORTED. The names below are TPF2's, unless marked *new*:

- **Commands:** `api.cmd.sendCommand(cmd, function(data, ok) ... end)`,
  with the factories `makeJournalBookAssetCmd`, `makeLineCreateCmd(name,
  color, player, line)`, `makeTownCreateCmd({TownInfo})`,
  `makeTownUpdateSizeCmd`, `makeTownUpdateCargoNeedsCmd`,
  `makeTownConnectWithIndustriesCmd`, `makeEntitySetNameCmd`,
  `makeStockListSetModifiersCmd` and `makeGameSetSpeedCmd` (named in a
  comment). The GUI state can send commands.
- **Engine:** `api.engine.getComponent`, `getEntitiesWithComponent`,
  `entityExists`, `api.engine.util.getPlayer`, `getWorld`, `getEntityName`,
  `api.engine.util.finance.getPlayersBalance` and `calculateBalance`,
  `api.engine.util.town.*`, `api.engine.system.transportVehicleSystem.getLine2VehicleMap`,
  `streetConnectorSystem.getConstructionEntityForIndustry`, and
  `api.engine.terrain.getHeightAt`, `isOnWater`, `isValidCoordinate` and
  `getBoundingBox`.
- **Components:** `TOWN` (`sizeFactors`, `cargoNeeds`), `INDUSTRY`,
  `CONSTRUCTION` (`transf`), `LINE`, `NAME`, `COLOR`, `STOCK_LIST`
  (`modifiers.productivity`), `TRANSPORT_VEHICLE` (`line`, `state`,
  `carrier`, `transportVehicleConfig`) and `GAME_TIME` (`gameTime`).
- **Types:** `api.type.Line` with `Stop` (`stationGroup`, `station`,
  `terminal`, `alternativeTerminals`, `loadMode`, `minWaitingTime`,
  `maxWaitingTime`, *new* `maxAdditionalWaitingTime`, `stopConfig`,
  `waypoints`), and on the line *new* `customFilters` and
  `reservationPriority` (the line priority in PLAN Part 3). Also
  `TownInfo` (*new* `initialLandUseCapacities`), `JournalEntry`,
  `StockList.Modifiers`, `Vec2f`, `Vec3f` and `Vec4f`.
- **GUI:** `api.gui.game.getGuiSaveData(key)` / `setGuiSaveData(key, table)`
  (*new*: a mod's own data, kept in the save), `isMapEditor`,
  `getEstimatedMaximumGameSpeed` (*new*), `api.gui.StyleSheet`,
  `api.gui.genericRep`.
- **Globals:** `debugPrint`, `_()` (translation), `pcall`, `math`,
  `string.format` and `table.sort`. `game.interface` is used by none of the
  mods, which does not mean it is gone. No mod uses `io`, `os` or `load`.
- The game ships Teal declaration files for its API (`system.d.tl` is
  cited by line), and its GUI and game rules as readable `.tl` sources
  (`game_bar.tl`, `game.tl`, `construction.script.tl`,
  `landmarks/hq/headquarter.script.tl`,
  `game_mechanics/towns/town_growth_metadata.tl`).
- The mods' author tried every cheat through an **in-game remote console**
  before adding a button for it. The game has a console, and a Debug Mode.

## What it means for the plan

These are consequences. None of them changes a decision in DECISIONS.md.
Two are questions for the team, marked *open*.

1. **Our mod and both probes will not load as they are.** They are TPF2
   mods. Before release day they need TF3's layout (`mod.json`,
   `_content.json`, `_metadata/`, `content/`). The probes also need a new
   way to run each step, since game scripts are not known to exist: a
   `GameBarInfoDisplayExtension` plugin with `react.onStep` runs in the GUI
   state and can read the engine through `api.engine.*`, as the mods show.
   The engine-state dump needs the run script's state, or a game script if
   one turns out to exist. The probes write files with `io`, which no mod
   shows. They must fall back to `debugPrint` into the game's log.
2. **Read the game's own sources first on release day.** The `.d.tl`
   declarations are the API reference that `script_api_dump` was built to
   reconstruct. `grep` over the game's `.tl` files for `api.cmd.make`
   lists the command factories and shows which UI builds which command.
3. **The caller-RVA filter may not tell a click from a replay.** On TPF2,
   only replays came through the script's `api.cmd` path. On TF3 the stock
   GUI is script, and script sends commands through that path. If the
   stock tools do, the road and track builders among them, a click and our
   replay of it
   reach `CommandList::Add` from the same place. The hook then needs
   another way to tell them apart, such as a flag the mod sets around its
   own replays. It may also be able to capture and cancel in script, by
   wrapping `api.cmd.sendCommand` in the GUI state, if that table can be
   written. Measure both on release day (BUILDING.md, "Measure these
   first").
4. **Speed and pause may not need native code.** Replacing
   `GameSpeedControl` catches the speed buttons. The keybinding
   `IA_GAME_PAUSE_OR_CYCLE_SPEED` changes speed as well, and must be caught
   too. The speed a room runs at can be any value, not only 1x to 4x.
5. **The in-game Multiplayer panel has a home.** A
   `GameBarInfoDisplayExtension` plugin in the game bar, and entity-window
   extension points for per-town and per-industry views.
6. *Open:* **Third-party mods that act from the GUI.** Big City and Startup
   Fortune send world-changing commands from `onStep`, once per save,
   remembered with `setGuiSaveData`. In a room, every player's game would
   send them. If the hook forwards them, the room builds one city per
   player. If it drops them, the worlds differ. The room's required mods
   (PLAN Part 3) need a rule for such mods before any are allowed.
7. **Game rules in script.** Construction costs, maintenance (cost / 6 per
   year when none is set, `construction.script.tl`), the headquarters'
   town growth bonus (+5%) and industry placement all live in the game's
   `.tl` files. `tpf3mp-canon`'s `Tf3Canonical` rules can be checked
   against them instead of against TPF2MP's model alone.
8. **Industry seeds.** A generated industry, and an industry's growth, is
   built with a random `seed` in its parameters. The build tool uses seed
   0. Replaying an industry (prospecting, PLAN Part 3) must carry the seed.
9. **Mod data in the save.** `setGuiSaveData` puts a mod's table in the
   save. That makes the save's mod data a thing to check before loading a
   received world (DAY_ONE.md §7). It can also hold a room's identity in
   its world, for rejoin.

## Still unknown after this

- The executable's name, anti-tamper, RTTI and assert strings. The mods
  touch no native code.
- The Lua version under Teal, and whether `io`, `os` and `load` exist.
- Whether game scripts (`res/config/game_script`) still exist.
- Where the game writes its log and `debugPrint` output.
- Whether the road and track builders build their commands in script.
- Whether build 40391 is the release build (the README's "a game update
  can break a mod" expects patches).
