# TF3 randomness and order survey -- 2026-09-29 (Steam build 40408)

What in Transport Fever 3 could make two games that run the same commands
at the same steps disagree: generators and their seeds, consumption order,
threading, floating point, and script randomness. Read statically from
`TransportFever3.exe` (SHA-256 `de1daad3...f23ef2`, image base
`0x140000000`, `.text` readable on disk) with `tools/tpfre`
(`C:\Users\james\TPF3-MP-builds\40408\tpfre-rng.db`) and from the game's
Teal/Lua sources under `base/` and `api/tealdef/`. The game was never run.
Companion pages: [TPF3_RECON_2026-09-29.md](TPF3_RECON_2026-09-29.md)
(the clock, the command pipeline), [docs/HOOKS.md](../docs/HOOKS.md)
"What lockstep needed beyond command capture" (the four TPF2 patches this
page looks for again), [docs/DAY_ONE.md](../docs/DAY_ONE.md) section 4.

Labels: **CONFIRMED** -- read instruction by instruction, or named by the
binary's own strings/RTTI, or in the game's script source; **INFERRED** --
concluded from code shape or from TPF2's design, not verified line by line;
**NEEDS-MEASUREMENT** -- only the running game can settle it. Classes:
**SIM** changes the simulated world; **PRESENTATION** changes only what one
player sees; **UNKNOWN**. Every RVA is for this build only.

## In one paragraph

TF3's simulation draws its randomness from generators the calling code owns
and seeds from game state (game time, update count, entity data, the map
seed), never from a clock or a global: the one framework RNG helper
(`random_util.cpp`) takes the generator as its first argument, the two
wall-clock seeds in the binary (`srand(time)` in `application.cpp`,
`mt19937(time)` in the new-game menu) feed one debug-only command applier
and the random seed *text* of a new game, and `math.random` in every Lua
state is the engine's own `boost::mt19937` seeded with the constant 5489,
not Lua's `rand()`. The three things that will diverge are the same three
that TPF2 needed patches for: the **order** a shuffle is applied to
(`LandVehicleMoveSystem::Update2` shuffles the vehicles that want track
with a `minstd_rand` seeded from the game time, over a list in ECS node
order -- the TPF2 train-order bug, now for every land vehicle), the
**order** claims are made in without a shuffle (ships and aircraft reserve
in node-list order), and per-edge **vehicle entry order** (min searches
with exact float compares over the entries of an edge). Threading is safe
by construction as far as the code shape shows: the thread pool splits
loops into at most 100 chunks by item count, not by core count, and
per-chunk results are gathered by chunk index. Floating point is one code
path (VEX/AVX, 18 FMA instructions in 13.6 M, no CPU dispatch in the game
itself); the CRT's `sinf/cosf/expf/powf/logf` remain a cross-CPU risk to
measure. Script randomness is deterministic where it is seeded from
`params.seed` (every construction script) and stream-order dependent where
it is not (`reforestation.script.tl`).

Counts: 17 SIM-side sources or order dependencies, 12 PRESENTATION-side,
4 UNKNOWN (tables below).

## 1. Native generators

### 1.1 The API: `framework/core/math/random_util.cpp`

Five exported helpers, all with `min <= max` asserts naming the file
(CONFIRMED). Each takes the **caller's generator** in `rcx`; there is no
hidden global in this file:

| RVA | shape (read from the code) | generator |
|---|---|---|
| `0x304e050` -> `0x48a6b0` | `int Random(gen&, min, max)`: `uniform_int_distribution` with rejection | `minstd_rand` (multiplier 0xbc8f = 48271, mod 2^31-1) |
| `0x304e0a0` | `float RandomFloat(gen&, min, max)`: `(draw-1) * 2^-31 * (max-min) + min` | `minstd_rand` |
| `0x304de80` | `float Random01(gen&)` | `minstd_rand` |
| `0x304df00` | `double Random01(gen&)` from two draws | `minstd_rand` |
| `0x304de20`, `0x304dfb0` | the same two with multiplier 0x41a7 = 16807 | `minstd_rand0` (one caller each: `procedural/streetgenerator.cpp` `0xce2800`) |
| `0x304e140` -> `0x3dcba0` -> `0x3df1f0` | `int Random(mt&, min, max)` | `mt19937` (twist at `0x3df1f0`) |
| `0x304e190` -> `0x3b1470` | `float RandomFloat(mt&, min, max)` | `mt19937` |

So determinism reduces to: who owns each generator, how it is seeded, and
in what order it is consumed. The generators found:

- **`std::mt19937` / `boost::mt19937`**: 33 seeding sites (`imul ..., 0x6c078965`,
  the 1812433253 init multiplier) and 13 twist bodies (`0x9908b0df`).
- **`std::minstd_rand`**: 36 functions with `imul r, r/m, 0xbc8f` (an earlier
  byte search on `8F BC 00 00` alone also hit `+0xbc` displacements of
  `TransportVehicle.stopIndex`; those are not generators).
- **`std::minstd_rand0`**: 2 helpers, 1 caller (street generator).
- **CRT `rand()`**: 4 callers; **`srand()`**: 2 callers.
- **`boost::random_device`** (`0x31742f0`, `CryptGenRandom`): 3 callers, all
  application start-up.
- No `mt19937_64`, xoshiro/PCG constants, or `std::shuffle` over any other
  engine were found. `std::shuffle` appears as inlined Fisher-Yates over a
  `minstd_rand` at three sites (below).

## 2. The map generator's seed path

CONFIRMED from strings and declarations:

1. The New Game menu generates a seed text with a wall-clock-seeded
   `mt19937` (`menuui.cpp` `0x6916d0`, section 1.2) unless the player types
   one; `UI::CMenuUI::StartNewGame` `0x6a5850` logs `"Seed text: {}"`.
2. `app.startGame2(map, seed : string, startDate, ...)` (`app.d.tl:60`)
   and `gui.setMapSeedText(seed)` (`gui.d.tl:868`) carry the text; the
   game-init function `0x117f40` logs `"Map seed text: {}"` and creates the
   `Lua_Game` state; `InitNewGame` (`gamesim.cpp`, `0x155630`, "Generating
   Terrain...", "Developing Town...", "Spawning Animals...") takes an
   `unsigned int` seed and runs the generator graph (`terrain::Feature::*`
   nodes on the thread pool, each with "Random Seed to Control the Noise
   Pattern" from `InputDataMapLayerGeneratorNode`). The map's `seed :
   string` is a field of `GameMap` (`type.d.tl:357`), i.e. it is saved.
3. `makeWorldReplaceTerrainCmd(map, terrainConfig, seedText, worldEntity,
   keepAssets)` (`cmd.d.tl:977`) regenerates terrain **through a command**
   with the seed text in its payload: replicated by construction.

Verdict: generation is a pure function of the seed text and the terrain
config (INFERRED for the noise nodes: their parallel `Apply` lambdas split
by item count, section 4), so a room that starts from one save is fine.
Two players who each press "New Game" with the same text should get the
same world but **must not** do so in a room: the town developer and
`RandomLocationFactory` run at generation with seeds derived from the map
seed, and any difference in mods, DLC or settings changes the result. The
room's world is the host's save (ARCHITECTURE.md), which already enforces
this.

## 4. Threading in the simulation

- **API**: the framework's own `ThreadPool` (`framework/core/ThreadPool.h`,
  ctor `0x3055a10` "ThreadPool::ThreadPool", `numThreads > 0`), with
  `Enqueue<T, F>(F&&, int, bool) -> JoiningFuture<T>`, `EnqueueDetached`,
  and `LoopImpl` (`0xe5160`, "numTotal > 0") whose splitter `0xe4260`
  computes `numTasks = ceil(numTotal / numPerTask)` and, when that exceeds
  `pool.maxTasks` (`[pool+0xc4]`, **set to the constant 0x64 = 100 in the
  ctor at `0x3055a9f`**), re-chunks to at most 100 tasks. Chunk boundaries
  therefore depend on the item count and the caller's `numPerTask`, **not
  on the core count**. `LoopResults<...>::LoopParallel` (`loopresults.h`)
  gathers each chunk's result vector and concatenates by chunk index
  (INFERRED from the RTTI `_Binder<lambda, int&, int&>` shape and the
  `LoopResults` name). PPL/ConcRT (`concrt140.dll`) is present only as
  `Concurrency::task` in the file dialog. `_Thrd_hardware_concurrency` is
  called from one framework helper (`0x304ad40`); the pools are created
  with explicit counts (e.g. the "GameScriptSystem Pool" from a setting,

## 5. Float determinism

- **One code path**: the binary is compiled for AVX (VEX encodings
  throughout, e.g. `vpxor`/`vmovups` in `application.cpp`, 33,820
  `vzeroupper`); no `__isa_available` dispatch of its own. `cpuid` (`0F A2`)
  appears 50 times, in the CRT's start-up (`0x318506c`, `0x30bd880`),
  glslang and displacement bytes, not in sim code. CONFIRMED.
- **No FMA contraction**: 18 `vfmadd*` instructions in 13.6 M (`C4 E2 ..
  A9/B9/99/A8/B8/98/AB/BB/9B/AD/BD/9D` counted), so the compiler did not
  contract `a*b+c`; Intel and AMD execute the same rounding. CONFIRMED.
  (macOS arm64 is a different compiler and will contract: DAY_ONE's
  expectation stands.)
- **The remaining cross-CPU risk is the CRT**: the game imports
  `sinf, cosf, tanf, asinf, acosf, atan2f, expf, logf, powf, fmodf, sqrtf,
  floorf, ceilf` and the double `sin, cos, tan, exp, log, pow, atan2, fmod`
  from `api-ms-win-crt-math-l1-1-0.dll`. The UCRT selects FMA3 or SSE2
  implementations of several of these at run time by CPU feature, which is
  the one known Intel-vs-AMD (and old-vs-new CPU) divergence source for an
  otherwise single-path binary. NEEDS-MEASUREMENT: DAY_ONE section 4's
  "Intel vs AMD, Windows" pair; if it drifts, the mitigation is a detour of
  those imports to one fixed implementation in the hook (a known technique,
  not planned here).
- **Order-dependent sums**: TPF2's `GetUsedSpace` `float` sum is not in
  TF3's `EdgeUseManager` (section 3); the min searches that replaced it are
  order-dependent only on exact ties. Other reductions were not surveyed.
- `-ffast-math`-style reassociation cannot be seen statically beyond the
  above; MSVC's default `/fp:precise` matches the absence of FMA.

## 6. Script randomness

- **The engine replaces `math.random` and `math.randomseed` in every
  `lua::State`** (`lua::RegisterRandomFunctions` `0x2fb1830`, reached from
  the state constructor `0x2faf4b0` on all four construction paths). The
  state owns a `std::shared_ptr<boost::mt19937>` (RTTI
  `_Ref_count_obj2<boost::random::mersenne_twister_engine<..., 1812433253>>`)
  seeded by `0x2fb2790` from the constant at `0x385c3e8` = **5489**
  (read from the file). `math.randomseed(n)` (`lambda_1` `0x2fb2360`)
  re-seeds that engine with the integer; `math.random(...)` (`lambda_2`
  `0x2fb2470`) draws a 32-bit word, scales by 2^-32 (`0x385c928`), rejects
  1.0, and implements Lua's `random()`, `random(m)`, `random(m, n)`
  ("interval is empty", "wrong number of arguments"). Lua is 5.2.2
  (`$LuaVersion` at `0x385d120`). CONFIRMED. So script randomness is a pure
  function of the call sequence since the state was created (or since the
  last `randomseed`), identical on every machine, and independent of the
  clock. It is **not saved**: after a load a state starts again at 5489
  while a running game's stream is far along -- the hot-join class of
  divergence only.
- **Every `math.random` in the game's scripts** (`base/`, 607 files; `dlcs/`
  has none), by file:
  - `content/buildings/townbuildingutil.lua:116-138`,
    `content/industries/industryutil.lua:384-535`,
    `content/industries/fieldutil.lua:233-613` (seven `randomseed(params.seed)`
    blocks), `content/industries/industry_productivity_util.tl:70-71`
    (`randomseed(construction.params.seed * 13 + 47)`): construction
    scripts, each `math.randomseed(params.seed)` first. SIM, pure functions
    of the construction's saved seed. CONFIRMED, harmless.
  - `content/terrain/reforestation.script.tl:54`: a **game script**
    (`.script.tl` with `update`/`handleEvent`, state in `GameScriptState`)
    computes `seed = gameTime + math.random(0, 1000)` with the **unseeded**
    stream and sends `makeWorldBuildProposalCmd(makeReforestationProposal(
    seed, ...))` through `api.cmd.sendCommand`. SIM. The draw depends on
    every earlier `math.random` in that state (the other game scripts share
    it if they share a state). Under lockstep this is fine only if (a) game
    scripts run identically on every game and their commands are applied
    locally, never sent to the room (DAY_ONE section 3 already requires
    this), and (b) the stream has consumed the same count on every game.
    (b) fails after a join or a resync (the joiner reloads: stream at 5489).
    Fix: the hook re-seeds the game-script state's `math.random` from the
    step number at each step (detour `lambda_1`/`lambda_2` or call
    `math.randomseed(updateCount)` from the mod before `update`), or the
    room forbids game-script commands and lets the host's copy through
    (worse: the host becomes special). NEEDS-MEASUREMENT: whether the
    reforestation command reaches `CommandList::Add` like a player's
    (TPF3_COMMANDS section 6 says it does not: the game-script states'
    send functor buffers or applies directly, never `Add`). **Built:** the
    per-step reseed, from `ecs::Engine::Update` on the simulation thread
    into both game-script states (`seeds.rs`; HOOKS.md "Seeds, as built").
    It covers every `.tl` rules script's `math.random`: `reforestation`
    (the one unseeded draw) by the per-step seed, and the construction
    scripts (`townbuildingutil`, `industryutil`, `fieldutil`,
    `industry_productivity_util`) because each calls
    `math.randomseed(params.seed)` first, so a per-step seed underneath
    them changes nothing. The other game scripts draw nothing. Map
    generation draws nothing from Lua's stream (section 2: the seed text
    and the native generators). Nothing else to build for scripts.
  - The other game scripts (`industry_workers`, `landmarks`,
    `landmarks_notification*`, `vehicle_modifier`, `transformator_townbuilding`)
    use no randomness. CONFIRMED (grep).
  - `math.randomseed(...)` never appears with `os.time`/`os.clock` in the
    base scripts; `os.*` is compiled into the Lua library (`os_time`
    `0x2fd04e0`, `os_clock` `0x2fd04a0`, `os_date` `0x2fd08a0`) and Mod Hub
    mods use `os.clock`/`os.time` (TF3_MODHUB_SCRIPT_MODS_2026-09-29.md), so a
    **mod's** game script can still seed from the clock. The probe's
    `math.random` and `os` checks (DAY_ONE section 3) decide the sandbox
    question; the answer for the base game is "deterministic".
  - Seeded engine services for scripts: `api.engine.util.getRandomTownPosition
    (town, seed)`, `createIndustryProposal(seed : string, ...)`,
    `makeReforestationProposal(seed, ...)` (util.d.tl:686, 951, 980). All
    take the seed from the caller; none reads a clock. CONFIRMED.
  - GUI-state scripts (`content/gui/**`) use no `math.random`; the GUI state
    is a separate `lua::State` with its own engine anyway. PRESENTATION.

## 7. What TF3's own lockstep ledger suggests

`CGame::Sync` `0x11f650` asserts `m_replicateTimes.size() ==
m_commandTimes.size() && m_replicateTimes.size() == m_stepTimes.size()` and
`m_data->singleReplTimes.size() == m_data->singleStepTimes.size()`;
`gui.d.tl:898-904` exposes `getReplicateTimes`, `getCommandTimes`,
`getGameStepTimes` "Only available in GUI thread"; `GameState::Replicate`
`0x255de0` copies the simulated state into the second `GameState` through
`ecs::Engine::Replicate` `0x2bb78f0` (`ReplicaCompVec<T>` per component
type, on the thread pool); `makeGamePerformSimulationStepsCmd` applies as an
atomic step budget (`0x9d894c`) that `GameSim::Step` drains. All CONFIRMED.

What it implies: the engine is built so that one `GameState` is advanced by
whole steps while the other is read, and a replica engine is kept equal to
the simulated one by copying components -- Urban Games needs the two
engines to agree, which is a determinism requirement of the same kind as
ours, and the `PerformSimulationSteps` budget is a ready-made step gate.
What it does **not** imply: that two *machines* agree. Replication copies
memory within one process; it never re-executes the step, so nothing in it
would surface a shuffle over node order, a `rand()` seed or a CRT `sinf`
difference. `Replicate` also does not copy the ECS node lists' order (they
are rebuilt per engine, INFERRED from TPF2), which is why TPF2's `step`
canon had to run on both engines of every peer.

## Pointing the determinism probe

`tools/probe/tf3/tpf3mp_detprobe_1` (DAY_ONE section 4) samples seven lanes
every 100 steps. Order the runs by what this survey ranks:

1. **Same PC, same binary, one save with a busy rail junction and a bus
   line with queued buses**: the `p` lane (vehicle positions) is the lane
   for items 1-4; sample every 25 steps for the first 3,000 steps, then
   every 100. Expect identical (TPF2 was, from one PC), which calibrates the
   lanes; the divergence is between machines.
2. **Two PCs, same save, no input**: `p` first, then `n` (people) and `t`
   (town buildings) -- the person and town systems draw from state-seeded
   generators over containers whose order is the open question (items 4, 9).
3. **Intel vs AMD**: `p` and `e` (edge geometry) for item 7; `c` (constructions)
   and `t` for growth.
4. **Different core counts** (or the thread-count setting): `p`, `n` for item 8.
5. **A join into a running room**: `e`/`c` (trees: item 6) and everything
   above, since a loaded game's node lists start in a different order than
   the host's (item 1's premise).

Add two lanes when the hook is in: a hash of the claim order at
`EdgeReservationManager::Reserve` per step (proves items 1-2 without
waiting for a position split), and the game-script state's `math.random`
draw count (item 6).
