# Windows Steam build 40444: the update of 2026-11-20

Transport Fever 3 updated on Steam from build 40425 (Steam build ID
26129055) to 40444 (26643808) on 2026-11-20. The 1.5.0 hook, built for
40425, refuses it: no compiled native bundle matches the new executable, so
multiplayer stays off (fail-closed). This note is the evidence for the new
bundle `profiles/tf3_build40444_steam_windows/`, now selected in
`profiles/native-build.txt`. It is static: the real-game acceptance
(GAME_TESTING.md) is listed as open at the end.

| identity | 40425 | 40444 |
|---|---|---|
| Steam build ID | 26129055 | 26643808 |
| SHA-256 | `e9a6190f…b9ca74cd` | `51a7cafa6b57bee804f1f513a9c58aa7a01a1d4ba3048c46e1fb4daa3d039c49` |
| executable size | 69,876,664 | 70,134,624 |
| PE timestamp | `0x6AD9CE10` | `0x6AF6FD97` |

The executable's own build string (`transportfever3`, `64-bit`, then the
build) reads `40444`. Unlike 40425, this is a code update: `.text` grew
and most functions moved.

## Inputs, and what was not available

A complete private `tpfre archive` of the installed game (6,168 files from
1,546 sources), outside Git:

```powershell
$b = "$env:USERPROFILE/TPF3-MP-builds"
& ./tools/tpfre/target/release/tpfre.exe archive --game 'C:/Program Files (x86)/Steam/steamapps/common/Transport Fever 3' --build 26643808 --steam-manifest 'C:/Program Files (x86)/Steam/steamapps/appmanifest_3493540.acf' --out "$b/26643808-sources"
& ./tools/tpfre/target/release/tpfre.exe verify "$b/26643808-sources" --profiles profiles --json
& ./tools/tpfre/target/release/tpfre.exe verify-build --repo . --archive "$b/26643808-sources" --json
```

With the bundle selected, `tpfre verify` matches all 170 targets of the
40444 profile, and `verify-build` exits 0 (`review_required: false`,
`runtime_verified: false`). The nine targets of `industry_probe.toml`, which
`verify` does not read, each match exactly once too.

The machine this was ported on had no archive of 40425 (Steam had already
replaced it), so `tpfre update --old … --new …` and its masked comparison
of every containing function could not run. In their place:

- **Signatures.** The 40425 profile with only its identity changed was
  verified against the 40444 archive: 159 targets matched uniquely, ten
  were missing and one prologue changed (below).
- **The 40408 index as the reference.** A `tpfre` index of the 40408
  executable (SHA-256 `de1daad3…`, the 40408 profile's) is on the machine.
  For each target, its containing function in 40408 and in 40444 was
  compared by size, instruction count, the target's offset in it, and the
  offset of every call and data reference, with each callee's size: 138
  targets' functions are identical in all of these. Of the 32 others, six
  are targets added after 40408, and the rest are reviewed below or were
  already known to have changed between 40408 and 40425 (the UI objects'
  growth in 40420 and 40423).
- **The emission code, proved.** With 40408's call and data targets (from
  its index) written back into 40444's bytes, the seven stretches the fast
  emission grid models (`Update`, three dispatchers, three kernels) hash to
  exactly the 40408 bundle's seven FNV-1a values: they are 40408's
  instructions, and 40425's, with only displacements moved.

Every fact the 40425 static proof asserts was re-read from the 40444
executable at its new place (`crates/tpf3mp-hookcore/tests/tf3_build40444_profile.rs`);
each relocated fact sits exactly at its neighbouring target's delta. The
40444 proof also asserts every byte the bundle's modules check at a site
before patching it, and the distances and frame slots they rely on.

## Changes that are more than an address

- **`RegisterAppUsertypes` takes five arguments.** 40444's function reads
  a `bool` in `r9b` (`movzx edi, r9b`) and, on the stack, a
  `std::shared_ptr` passed by value (`mov rax, [rbp+0x520]`: the entry's
  `[rsp+0x28]` after seven pushes and `lea rbp, [rsp-0x4c0]`); each of its
  three callers passes both (`mov r9b, 1` or a byte, and `[rsp+0x20]`
  pointing at a copy whose count it raised). MSVC hands a by-value object
  over as a pointer to the caller's copy, and the callee releases it. The
  hook's detour passed four registers through, so the game would have read
  its fifth argument from the detour's own frame and released whatever lay
  there. The detour now passes the first stack argument through as well
  (`menu.rs`, `RegisterPassthrough`, with a test); on a build whose function
  takes fewer arguments the extra word is read from the caller's frame and
  ignored. The new signature holds both reads, so a build that changes the
  arity again does not resolve.
- **The transport vehicles' node count moved in its frame.**
  `ecs::TransportVehicleSystem::Update2` (vf12, `0xb94d80`, 50 instructions
  longer than 40408's) still spills its `int` count to its home slot
  (`mov [rax+0x18], r8d`), but its frame is now `lea rbp, [rax-0x578]`, so
  the count is at `[rbp+0x590]`, which the visit loop runs to
  (`cmp [rbp+0x590], ebx`). `order.rs`' `platform::COUNT` is `0x590`
  (`0x5b0` on 40425). The order fix checks the count against the list's
  length, so the old value would have refused the fix, not misread the list.
- **The street tool's click callback was recompiled.** The callback
  (`0x56eb70`, `street_util::SnapPointBaseEdge`'s) compares with a zeroed
  `r13` and branches long, and its direction block moved past its
  epilogue. What it does is unchanged, read instruction by instruction: the
  command's result (`+0x30`), the functor's continue byte (`+0x28`) and
  `[[tool+0x960]+0x8e0]`; the payload's edges at `+0x18`, `0x350` bytes
  each, matched at `+0x10`/`+0x1c`; the end node's edges counted, streets
  by their `BaseEdgeStreet` and the others by `roadType` 0; the snap point
  `{edge, 0 or 1.0f (0x36c5714), 0, word 1, zeros}`; and the direction, the
  end's tangent (`+0x34` as is, `+0x28` negated) normalized, `+0xd` the
  tool's kind byte, `+0x10` set, only when the settings ask for it and one
  edge of the tool's network meets there. That is what `toolchain.rs`
  hands `StartAt`. Its distances are new: `SCAN_TO_SNAP` `0x2a9` (was
  `0x2b9`), `SNAP_CALL` `0x58` (was `0x50`).

Shape changes seen, no constant affected:

- `builder_renderer_util::AddToRenderer` (`0x5e3130`) is 54 instructions
  shorter and no longer reads its sixth and seventh arguments (the offset and
  the entity map). It keeps its ten arguments: every one of its twelve
  callers, the ProposalViewer's among them, passes ten. The hook's call
  passes the same ten as before.
- `UI::StationViewer::vf4`, `UI::layers::CatchmentAreaHelper` and
  `LayerManagerColorMap` differ from 40408's by a few instructions away
  from the sites. Each of the 19 GUI player sites still follows the load
  of the player (`[x+0x20c]`) into the register the bundle names, and each
  owner test still compares through its register.
- `UI::StreetBuilder::Step`, `UI::ConstructionBuilder::Step` and
  `UI::Bulldozer::Step` changed; the tool player writes each tool's own
  player field at its frame, and the six constructors' stores those fields
  are read from are 40408's.
- Two callees of the emission code changed: the dispatchers' thread-pool
  helper (`0x11d9c0`), which the fused step does not use, and a function
  `Update` calls (`0xab1680`), which stays the game's.

## Native data: what changed

- `netread.rs`: the five `CompVec<T>` pool vtables, each `+0x2f0e0`
  (BaseEdge `0x36cebe8`, BaseNode `0x36cec58`, BaseNodeConfig `0x36cecc8`,
  Construction `0x36cf630`, RailroadCrossing `0x36cf208`), slot 0 their
  own `vf0`. Every size and offset unchanged.
- `network.rs`: `EDGE_VTABLE` `0x379fa10`, `NODE_CONFIG_VTABLE`
  `0x379fa50` (`UserdataValue<BaseEdge>` / `<BaseNodeConfig>`), each slot 0
  its `vf0`; allocation sizes, payload and the `laneConfigs` registration
  unchanged.
- `simperf.rs`: the wrapped slots, `EmissionGridSystem` `0x374c6e0`
  (vtable `0x374c688` slot 11), `EmissionEmitterSystem` `0x374c060`
  (`0x374c000` slot 12), `TownSystem` `0x3758798` (`0x3758738` slot 12),
  each holding its profile target.
- `emission.rs`: the seven FNV-1a hashes (the code proved 40408's above);
  offsets, lengths and every field unchanged.
- `savefast.rs`: `LEVEL_LOAD_BYTES` (`8B 05 6E 69 4E 03`, the constant at
  `0x3814b98`).
- `industry_schedule.rs`: the shared state's control block,
  `std::_Ref_count_obj2<IndustryChainSpawnState>`, vtable `0x36cc2a0`, its
  slots `0x15bbd0` (destroy) and `0x63e30` (delete).
- `toolchain.rs`: `SCAN_TO_SNAP` and `SNAP_CALL` (above).
- `order.rs`: `platform::COUNT` (above).
- `edgewatch.rs` `PATHS` (log labels only): `0x11efc6` queue, `0x1208ef`
  script, `0x120764` direct, the three calls of `CommandApply::One`
  (`0x9ea300`).
- `native.rs`: Steam build ID and game build; `hooks.toml` and
  `industry_probe.toml`: the identity.

Unchanged, each checked on 40444 by the proof: the command layout (the
street callback still tests `[payload+0x9b8] == 0x34`, 52); every splice's
bytes in `guiplayer.rs`, `toolplayer.rs`, `persons.rs`, `order.rs`,
`edgewatch.rs`, `streettrace.rs`, `ticks.rs`, `townfield.rs`,
`towntrace.rs`, `crossings.rs` and `probe.rs`, with the distances between
their sites; the CMenuUI fields (`m_game` `+0x8d8`, `m_loadGameResult`
`+0x1df8`) and the drawing anchors' fields (`+0x8e0`, `+0x7b0`, `+0xe18`,
`+0x760`, upload `+0xf0`); the step cadence: `CGame::Step` (`0x11f7e0`),
`CGame::Sync` (`0x11fa80`) and `RunGameSimLoop` (`0x11e640`) are 40408's
in size, instructions and the place of every call and reference, with the
same fields, so `interval.rs`' layout holds and 40444 joins its builds;
`CGame::Step`'s first 31 bytes (`pacing.rs`) and the span fill
(`fastbitmap.rs`), byte for byte.

The proposal layouts `modules.rs` reads and `terrain.rs` writes have no
site of their own to check. Their element sizes are still the code's: a
`ConstructionEntity`'s `0xe48` is the stride of 35 `imul`s and 59 `add`s in
40444's `.text` (no `0xe40` or `0xe50` appears anywhere), a segment's
`0x350` of 53 and 200, an edge object's `0x1a0` of 57 and 148, and the
`Proposal`'s `0x358` of 18 `add`s. The street callback above reads
segments at the same `0x350` stride and fields. The functions that fill and
apply proposals (`CreateProposalData`, the module editor's and the
`ProposalAction`'s `Add` calls, `WorldBuildProposal apply`) are 40408's in
shape. A changed field offset inside an unchanged size would not show
here; the real-game run below covers those reads.

## Scripts

There was no 40425 archive to compare every script with, so only the files
the mods copy, wrap or depend on were checked:

- `gui/line_vehicle_mgmt/manager_window.tl` **changed** (SHA-256
  `d94adf0d…`, was `9608c068…`): line problem and capacity filters. The
  mod's copy is rebuilt from 40444's file with its one change re-applied
  (the stations clicked while a new line is being created, queued and added
  once it exists, four marked blocks); every game function it calls is
  still there (`line_util.isStopProtected`, `makeNewStop`, `autoLoadConfig`,
  `reactLineCommit`). `tools/teal/check.py` finds no error the game's own
  file does not have. The copy is pinned to the 40444 executable.
- `gui/menu/main_page.tl` is unchanged (`56191b18…`).
- `api/tealdef/api/cmd.d.tl`: every constructor it declares is one the
  repository already knows; the guard refuses any it does not carry.
- Big Maps' copy of `gui/menu/new_game_or_map_settings_page.tl`: 40444
  added `getInstalledActiveMods` (the active mods that are installed) and
  uses it twice, and renamed a comment. With its marked blocks put back to
  the game's lines, the copy equals 40444's page; `check.py` finds no new
  error. `base/difficulty_util.tl`'s `getScale`, which Big Maps wraps,
  keeps its signature.

## Big Maps' plugin

The package is pinned to one executable, so the 40425 package is refused on
40444, as it must be. `src/build40444.rs` replaces `build40425.rs`: every
signature matches once and every byte its checks read holds, but for these
displacements: the two vtable `lea`s (`grid_slot` `48 8D 05 A8 A9 C9 02`,
`emitter_slot` `48 8D 05 DB E3 C9 02`, each reaching its vtable), three call
displacements and the factor load's in `CREATE_GRID_BODY`, and the coarse
factor: the 0.0625f is at `0x36f2d84` (read by 11 instructions) and the
0.125f the load is pointed at is now `0x3702324` (read by 22), `0xf5a0`
apart (was `0xf540`; the old distance would reach a denormal).
`tests/game_40444.rs` passes against the 40444 executable and profile. A
40444 package must be published (and the shipped registry's repository
updated) for players who use Big Maps.
