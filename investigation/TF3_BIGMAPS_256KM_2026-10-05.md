# Big maps with a 256 km edge on TF3: every wall, memory, and a plan

2026-10-05. Static analysis of Transport Fever 3 Steam build 40408 (SHA-256
`de1daad3…f23ef2`, image base `0x140000000`) with `tools/tpfre`, and the
Stage 0 measurements. No game was started. Addresses are RVAs.

The goal: a map whose long axis is **1,000 tiles of 256 m (256.0 km)**.
This note lists every wall such a map meets, what each one needs, what
memory it costs, and the order to build it in. It extends
[TF3_BIGMAPS_PORT_2026-10-01.md](TF3_BIGMAPS_PORT_2026-10-01.md) (the
port plan, "the port note" below), whose tags it uses:

- **CONFIRMED-static:** read from TF3's bytes; each says how.
- **MEASURED:** read from a TF3 game log or process.
- **DERIVED:** computed from the above, not seen in a running game.
- **NOT FOUND:** looked for and not located.

The TF2 counterparts are silver2127's tpf2-bigmap (read-only input):
`docs/octree-depth12.md`, `docs/placement-distance.md`, the README's
street raster section, `src/octree_depth12.h`, `src/placement_distance.h`.
No code is taken from it; the patch shapes follow its design.

## Summary

| wall | limit | at 1,000 tiles long | needs | status |
|---|---|---|---|---|
| Octree root | depth 10: ±32,768 m (256 tiles); depth 11: ±65,536 m (512 tiles) | ±128,000 m: **depth 12** (±131,072 m, 1,024 tiles) | depth 11 is a root rewrite; depth 12 also deep ids and a decoder patch | depth 11 built and seen in game; depth 12 built (see "Depth 12, built"), not tested in game |
| Street/obstacle raster | `(256·nx+1)(256·ny+1) ≤ 2³¹−1` at 1 m | 1 m fits only up to 1000 × 32 | a coarser cell, only where 1 m overflows | built (Stage 3) |
| Placement spacing | int32 squared pixel distances: pairs ≤ 185.4 km | every 1,000-tile map has pairs 256 km apart | 64-bit distances saturated at `INT_MAX` | built (Stage 3) |
| Heightmap element count | `(64·nx+1)(64·ny+1) ≤ 2³¹−1` | short side ≤ 524 tiles | nothing below that | not reached: memory binds first |
| Memory | 10.25 MB/km² + 5.8 GB (MEASURED at stock sizes) | 65.5 km² per short tile | a big machine | the binding wall |
| Float precision | f32 ulp at 128 km is 7.8 mm | | nothing | DERIVED, no wall |
| Wire positions (D8) | i32 mm = ±2,147 km | | nothing | no wall |

**The 256 km × 256 km square is impossible:** 65,536 km² at the measured
law is 677,544 MB of generation peak, about 678 GB. The 256 km edge is
reachable only as a thin map: on a 128 GB machine, 1000 × 186 tiles
(256 × 47.6 km).

## 1. The octree root (CONFIRMED-static)

The root is TF2's two-tier constant, set at two sites (the port note,
§1.3), re-verified today:

- `OctreeSystem::Resize` `0xae4c50` (101 bytes) stores `-half` at
  `+0x10..+0x18`, `+half` at `+0x1c..+0x24` and the depth at `+0x28`;
  nothing else. It brackets the stores with two calls of `0x55b50`, which
  is `ret 0` (an empty profiling scope). Verified by disassembly.
- Its only callers are the two root sites, each `cmp [tiles],0x80 / jg /
  cmp [tiles+4],0x80 / jle`, then `vmovss xmm2,[0x3683038]` (32768.0f),
  `mov rcx,[owner+0x38]`, `mov edx,10`, `call Resize`:
  - **init** `0x244b8b` in `0x244b00` (new game, `InitGame`): tiles in
    `rbp`, owner in `rsi`; the next instruction, `vmovss xmm2,[rbp+0x20]`
    at `0x244ba1`, is also the `jle`'s target.
  - **load** `0x20267d` in `0x2024a0` (`GameState::Load`): tiles in `rsi`,
    owner in `rbp`; next `vmovss xmm2,[rsi+0x20]` at `0x202693`.
  - The 36-byte patterns from the `jle` to the instruction after the call
    each match once in `.text` (`tpfre q bytes`), and differ only in the
    owner and tiles registers.
- The descent (TF2 `0xa507e0`, "NOT FOUND YET" in the port note) is
  **`0xae33c0`**, found today:
  - It is recursive (it calls itself at `0xae38cd`), and its only other
    caller is `0xae3950`, called by `OctreeSystem::vf4` (`0xae2920`) and
    `vf9` (`0xae215f`).
  - Its failure path asserts `m_nodeCompTypeIndex >= 0` in
    `detail::EcsOctreeIterator<ecs::OctreeSystemData>::EcsOctreeIterator`
    (`Game/ecs/EcsOctree.h`): it returns an iterator to the leaf found or
    created.
  - The child id is TF2's: `lea r9d,[rax*8+1]; add r9d,r12d` at
    `0xae3889` computes `8·id+1+octant` in 32 bits from the incoming id
    (`r9d`, kept at `[rsp+0x54]`).
  - Ten arguments (Windows x64): `rcx` the octree (`OctreeSystem+8`:
    `[+0]` the engine, `[+0x28]` the node component type), `rdx` the
    iterator returned, `r8d` the parent node's entity, `r9d` the node's
    id, then on the stack the octant (`+0x28`), two pointers to the
    object's position and extent (`+0x30`, `+0x38`), **the remaining
    depth** (`+0x40`), the node's box (`+0x48`) and the node's entity,
    `-1` when it does not exist yet (`+0x50`).
  - The starter `0xae3950` passes `r8d = -1`, `r9d = 0`, octant `-1`, the
    box from `OctreeSystem+0x10`, the depth from `OctreeSystem+0x28` and
    the root entity from `OctreeSystem+0x2c`.
  - A node is created only when its entity is `-1`; then the id is
    written once, into the new `EcsOctreeNode` (parent at `+0`, id at
    `+4`, box at `+8`, eight child entities at `+0x98`, their valid flag
    at `+0xb8`), and the node is recorded in its parent's children. For
    an existing node the incoming id is used only to compute its
    children's.
  - `sub dword [remaining],1; jne` at `0xae373b` stops one level above
    zero, so a tree of depth `d` has levels `0..d-1` and the root counts
    as a level, as in TF2. At depth 10 the leaves are 65,536 m / 2⁹ =
    128 m.
- The renderer's level decoder `CalcOctreeLevel` is `0x818b30` (port
  note), its loop `0x818b70-0x818b84` the only copy in `.text` (the
  14-byte loop body and a looser `lea r,[r*8]` pattern each match once).
  It is called only from `0x2f345b` in `0x2f30b0`.

**What each depth needs (DERIVED from the above):**

- Level `L` starts at id `(8^L − 1)/7`. Depth 11's deepest level, 10,
  ends at id 1,227,133,512 (`0x49249248`): it fits a positive int32, and
  the decoder's loop exits correctly for it (its last threshold,
  1,227,133,513, is still positive). **Depth 11 needs only the root**:
  depth 11 at ±65,536 m keeps 128 m leaves.
- Depth 12's level 11 would start at 1,227,133,513 and end at
  9,817,068,104: past 32 bits. Worse than wrong ids: in the decoder,
  after level 10 the step `lea r8d,[r8*8]` wraps to 0, so for any id at
  or above 1,227,133,513 the loop never ends. **Depth 12 with stock ids
  would hang the renderer's skip pass**, not just mis-draw.

## 2. The street and obstacle raster (CONFIRMED-static)

- `Obstacle::Obstacle` `0x8cea50` (`this` `rcx`, box `{minX, minY,
  maxX, maxY}` at `rdx`, cell `xmm2`) stores the box at `+8`, the cell at
  `+0x18`, then `n = floor(extent / cell) + 1` per axis (`vdivss`,
  `vcvttss2si`, a `-1` for negatives, `inc`) into `+0x40`/`+0x44`, and
  sizes the `vector<bool>` at `+0x20` with `imul eax,edx; movsxd rdx,eax`
  (`0x8ceae5`): TF2's 32-bit wall.
- Its five calls: `CreateAndAddIndustry` `0x8f1ca0` (`0x8f219e`, cell
  from the caller's frame), the town connections in
  `init_streets_util.cpp` `0x8feba0` (`0x8ff06d`), `0x912940`
  (`0x9129c3`, cell `[0x3676644]` = 1.0) and the native map preview
  `0x28dca20` (twice, `0x28dcd46`).
- **The cell is honoured downstream** (CONFIRMED-static for what is
  listed):
  - `Obstacle::vf4` `0x8cece0` (`HasObstacleAt`, by world position)
    divides by the stored cell `[+0x18]`;
  - `Obstacle::vf2` `0x8cec40` returns the cell, `vf1` the counts;
  - the only fill, `0x912940`, rasterises through
    `BitmapRasterizable` and `0x2b6a790`, whose scale is
    `extent / (n − 1)` from the same box and counts, not a constant;
  - `Obstacle::vf3`/`vf4` have no direct callers (they are reached only
    through the `IObstacle` vtable), and the `vf1` calls are the fill's.
  - Every obstacle query found in `init_streets_util.cpp` is a `[+0x20]`
    virtual call, `HasObstacleAt` by position (that these calls are on an
    `IObstacle` is DERIVED from the slot and the argument shape).
- **One subtlety the fix must respect** (DERIVED): the fill scales by
  `extent/(n−1)` while lookups divide by the cell. They agree exactly
  only when the cell divides the extent. With 1 m cells and whole-metre
  boxes they always do; with a 3 m cell on 256,000 m they drift by up to
  a third of a cell across the map. So the fix grows the cell in **powers
  of two**: tile edges are 256 m, so 2, 4 and 8 m divide every whole-tile
  extent, and the float divisions stay exact.

At 1,000 tiles long, 1 m cells fit only up to 1000 × 32 (256,001 ×
8,193 = 2.097e9). 2 m cells fit up to 1000 × 130, 4 m cells to well past
anything memory allows (1000 × 186 at 4 m: 64,001 × 11,905 = 0.76e9).

## 3. Placement spacing (CONFIRMED-static)

`0x8d31f0` (port note: "by the loop shape") is TF2's `0x910ce0` in
every detail read today:

- Arguments: `rcx` the output `vector<float>`, `rdx` the candidates
  (`{int32 x, int32 y, float angle}`, 12 bytes), `xmm2` the minimum
  distance, `r9` the exclusions (`{int32 x, int32 y}`), the resolution on
  the stack (`[rsp+0x28]` at entry).
- A scratch `int32` per candidate filled with `0x7fffffff`; for each
  candidate `i`, every later `j` gives `d = dx·dx + dy·dy` in **int32**
  (`imul edx,edx; imul eax,eax; lea ecx,[rax+rdx]` at `0x8d334b`),
  folded into `i`'s running minimum and into `j`'s scratch; then the
  exclusions the same way (`0x8d33ab`); then `distance =
  sqrt(float(best) · resolution²)` and `out[i] = min > distance ? 99999
  : min / distance`.
- One caller, `0x8d6390` (`0x8d63df`), next to
  `RandomLocationFactory` (`0x8d2310`).
- Separations past √(2³¹−1) = 46,340 px (185.4 km at 4 m) wrap: negative
  squares give NaN scores, wrapped positives false proximity.

Every 1,000-tile map has candidate pairs 256 km apart, so the fix is
needed for the goal; up to 724 tiles on the long axis it never changes a
result.

## 4. The heightmap (DERIVED)

`(64·1000+1)·(64·ny+1) ≤ 2³¹−1` gives **ny ≤ 524 tiles** (134 km) at
1,000 long. The memory wall (§6) comes far earlier, so this is not a
constraint in practice.

## 5. Other walls

- **Float precision (DERIVED).** Positions are f32. At ±128 km the ulp is
  2⁻⁷ m = 7.8 mm (stock 250-tile maps: 3.9 mm at their edge). TF2 maps of
  292 km were played (tpf2-bigmap's depth-13 test) without reported
  jitter. Not a wall; worth watching on vehicles at the far edge.
- **Wire positions (D8):** i32 millimetres, ±2,147 km. No wall.
- **16-bit tile indices:** none seen in the sites above (the raster, the
  octree and the heightmap index in int32). A full search of every tile
  index was **not done**; a 1000 × 186 map has 186,000 tiles, past
  65,535, so an in-game test must watch for it.
- **The New Game preview** (`builtin.MapPreviewComp`, CONFIRMED-static in
  the port note) generates the whole map, towns and industries included,
  on every change, so it meets the same memory wall as generation and
  calls the raster constructor itself (`0x28dca20`).
- **Per-tile render data (NOT MEASURED on TF3).** TF2 kept a 67,601-byte
  material grid per tile for good; TF3 has the same cell (port note
  §1.2). If TF3 keeps it, 186,000 tiles hold 12.6 GB of it after entry.
- **Load and autosave timeouts, snapshot size:** a world of 30 times
  Gigantomaniac's area outgrows the 5-minute load and 20-second stall
  defaults (OPERATIONS.md, "Big maps"). DERIVED, not measured.

## 6. Memory (MEASURED law, DERIVED sizes)

Stage 0 measured, at stock Gigantomaniac only: 10.25 MB per km² of
terrain toolkit (temperate; 12.25 in an older subarctic log) plus 5,800
MB of the game's own at generation's peak
(`crates/tpf3mp-bigmap/src/memory_gate.rs`). A tile is 0.065536 km², so
each short-axis tile of a 1,000-tile map costs 671.7 MB at 10.25 (802.8
at 12.25). The law is a straight line through one size; 30 times that
area is an extrapolation.

| machine | largest 1,000-tile-long shape (temperate, 10.25) | km | area | expected peak | street cell | subarctic (12.25) |
|---|---|---|---|---|---|---|
| 32 GB (32,768 MB) | **1000 × 40** | 256 × 10.2 | 2,621 km² | 32,670 MB | 2 m | 1000 × 32 |
| 64 GB (65,536 MB) | **1000 × 88** | 256 × 22.5 | 5,767 km² | 64,913 MB | 2 m | 1000 × 74 |
| 96 GB (98,304 MB) | **1000 × 136** | 256 × 34.8 | 8,913 km² | 97,157 MB | 4 m | 1000 × 114 |
| 128 GB (131,072 MB) | **1000 × 186** | 256 × 47.6 | 12,190 km² | 130,744 MB | 4 m | 1000 × 156 |
| any | 256 km square, 1000 × 1000 | 256 × 256 | 65,536 km² | 677,544 MB (≈ 678 GB) | — | — |

The peak is held against physical memory with no margin, as the gate
does today, and a machine reports a little less than its round size, so
each row is the edge. And every machine in a room must **load** the
world, not only the host generate it: after entry stock Gigantomaniac
held about 13.4 GB, and nobody has measured what a world 15 times its
area holds after entry.

## 7. Multiplayer

Neither the octree depth nor the raster cell nor the placement
arithmetic is in the save: each game derives them at world allocation
from the tile counts and its own code (port note §3). So:

- **Every patch here is derived from the world, not from a size the
  player picks.** Each one changes nothing unless the world needs it:
  the root moves only for an axis past 256 tiles, the cell grows only
  where 1 m overflows (where stock code aborts), and the 64-bit
  distances differ from stock only for pairs past 185 km. A stock-sized
  or Stage 1 world runs stock code in every game, patched or not.
- **Each patch is opt-in** in the game's environment, off by default, and
  fails closed: a site whose bytes are not exactly the profile's leaves
  the game stock and logs why, and the big sizes must not be offered on
  that game.
- **Not enforced yet:** a room cannot yet see whether every game applies
  the same patches. Until the hook reports them (port note §3: a
  `tpf3mp:bigmap` entry in the content manifest), a room on a world past
  256 tiles needs the same settings in every game, as `tpf3mp_bigmap_1`
  is needed for the density levels today (docs/BIGMAPS.md). A game
  without the octree patch loading such a world loses entities past
  32.8 km to lookups and damages the save.

## 8. The plan, and what was built

Each step is its own commit on `feat/bigmaps-256km`.

1. **This note.**
2. **Stage 2: depth 11, up to 512 tiles (131 km).** A splice at the
   instruction after each root call: when the setting is on and an axis
   of the world being allocated is over 256 tiles, it calls the game's own
   `Resize` again with depth 11 and ±65,536 m. No shared constant and no
   game byte other than the splice's jump changes. The bigmap crate
   learns TF3's ceiling (depth 11 is the deepest this build reaches) and
   gets a Stage 2 settings file.
3. **Stage 3: the raster and placement.** A detour of `Obstacle::Obstacle`
   that, only when the stock cell's count would overflow int32, grows the
   cell through 2, 4, 8 … m until it fits; and a detour of the spacing
   score that computes the same scores in 64 bits, saturated at
   `INT_MAX`. Both are tested against the **original machine code**,
   relocated from the executable into the test process.
4. **The ratio dropdown** past 1:5 (1:6 to 1:10), each shape gated by the
   same ceilings and memory law, so long edges are reachable from the New
   Game page.
5. **Depth 12: not built.** The descent and the decoder are found (§1),
   but three things are missing before it can be proven statically:
   - every reader of the node id. Known: the decoder `0x818b30` and its
     caller `0x2f30b0`. TF2 also found its skip manager's per-level
     vector, sized from the box width and the depth (TF2 `0xa503e0` /
     `0x852940`); TF3's counterpart is **NOT FOUND**. A level past that
     vector's size is silently skipped, or worse.
   - proof that node ids never reach the simulation. Compact ids drawn
     from a counter depend on the process's history (two loads of one
     world number their deep nodes differently), so if any simulation
     path orders or hashes by node id, two games in a room diverge. TF2
     did not need this proof for a single player; a lockstep room does.
   - an offline run of the descent `0xae33c0` with the id hook, as TF2
     ran its descent in Unicorn. Its body calls the ECS
     (`0x2bb3760`, `0x2bb2360`, `0xade7b0`, `0x2d91c0`, `0xa4b90`,
     `0xadf100`), so running it in a test needs those stubbed with a
     model of the component store.

   The shape it would take, from the arguments in §1: an inline detour of
   `0xae33c0` (prologue `48 8B C4 48 89 58 18 55 56 57 41 54 41 55`, no
   RIP-relative operand) that, when `depth − remaining ≥ 11` and the
   node's entity is `-1`, replaces `r9d` with the next id of a compact
   range per level (`0x50000000 + n` for level 11, `0x60000000 + n` for
   12, as TF2); an existing node's incoming id is only used for its
   children's, which the detour replaces in turn; a rewrite of the
   decoder loop at `0x818b70` that answers `(id >> 28) + 6` for ids at or
   above `0x50000000`; and the root at depth 12, ±131,072 m.

## 9. What a person must test in the game

None of this has run in a game. For each step, on a machine with the
memory for the size, starting the game from the launcher with the
setting on, and a second run with it off:

- **Stage 2 (depth 11):**
  - generate 1:5 at 60 × 300 (77 km long, about 1,180 km²); `hook.log`
    shows the octree line for both the new game and, after a save and
    reload, the load;
  - the game log has no `Duplicate base nodes` line, and towns past
    32.8 km from the centre grow streets and population;
  - with the setting off, a stock Gigantomaniac and a Stage 1 176² world
    behave exactly as before (no octree line in `hook.log`);
  - a room of two games (Sandboxie), both with the setting, on the 60 ×
    300 world through `tools/scenarios/roads.json` and `rail.json`:
    checkpoints agree.
- **Stage 3 (raster, placement):**
  - generate 300 × 300 or the largest square memory allows past 180²;
    `hook.log` shows the raster line with 2 m cells; generation does not
    abort, and towns get streets;
  - generate a long map past 724 tiles only once depth 12 exists; until
    then, the placement fix changes no result and is checked only by
    the offline test;
  - a room of two games founding industries on a world past 180² (the
    raster is rebuilt for every founding): checkpoints agree.
- **The ratio dropdown:** 1:6 to 1:10 show for the rows whose shapes
  fit, the note names the reason for those that do not, the preview
  regenerates at the shape picked, and a save's `map.format` reads 1:5.
- **Memory:** for each new shape, Stage 0's measurements (toolkit maps
  and MB, peak private bytes in generation, after entry and after load,
  save size and time), to check the straight-line law far past stock.
- **Depth 12:** nothing to test until it is built.

## Addendum: what was built, and depth 12's next steps

Built on `feat/bigmaps-256km` after this note (each opt-in, derived from
the world, and tested against the game's own code relocated from the
executable, `crates/tpf3mp-hook/src/bigmap/`):

- Stage 2, the depth-11 root: `TPF3MP_BIGMAP_OCTREE=11`.
- Stage 3, the street raster: `TPF3MP_BIGMAP_STREET_RASTER=1`; placement
  spacing: `TPF3MP_BIGMAP_PLACEMENT=1`.
- The ratio dropdown's 1:6 to 1:10 in the mod's page copy.

**Depth 12 stays unbuilt.** Where to look next, from the skip pass that
calls the decoder (`0x2f30b0`): its other callees in the skip manager's
file, `0x8189e0` and `0x818cb0`, are the first candidates for the
per-level vector the decoder indexes (`[skip+0x108]`, 24-byte entries);
whatever sizes it must be shown to size by the root's real depth, or a
level-11 node is skipped. Then every reader of `EcsOctreeNode+4` (the id),
and a proof that none of them reaches the simulation, before a compact-id
detour of `0xae33c0` can be offered in a room. Until then the bigmap crate
blocks every size past 512 tiles on TF3 (`octree_max_depth` 11), and a
256 km edge is not offered.

## Depth 12, built (2026-10-05)

Built on `feat/bigmaps-256km` behind `TPF3MP_BIGMAP_OCTREE=12`
(`crates/tpf3mp-hook/src/bigmap/depth12.rs`, `octree.rs`). Not tested in
the game yet.

### Every reader of the node id, and of the depth (CONFIRMED-static)

The node component, `ecs::component::computed::EcsOctreeNode<OctreeSystemData>`,
is 0xc0 bytes (the component vector's stride in the iterator's
dereference `0x2fe150`, `lea rax,[rax+rax*2]; shl rax,6`): parent entity
`+0`, **id `+4` (int32)**, loose box `+8` (the cell grown by half a cell
each way), eight child entities `+0x98`, their valid flag `+0xb8`. It is
a "computed" component, rebuilt on load, not saved.

- **Writer:** only the descent `0xae33c0`, once, when it creates a node
  (`mov [rbp-0x3c],r10d` into the data `0xade7b0` adds). The only
  `8·id+1+octant` in `.text` is its `0xae3889` (every `lea r,[r*8+1]` form
  was searched; the other hit, `0xb2be0e` in `SimPersonSystem`, is a
  vector size). An existing node's id is never rewritten; the incoming id
  only seeds its children's.
- **Readers:** of the 195 calls of the iterator dereference `0x2fe150`,
  the integer reads of `+4` are four, all in the renderer's static-LOD
  code (`CRenderer::Data::StaticLodRange`, `loopresults.h`): `0x2f3455`
  (the id into `CalcOctreeLevel` `0x818b30`), and `0x2f1f71`, `0x2f3c19`,
  `0x2f4759`, each building a 64-bit key `0x3000000000000000 | x << 32 |
  sext(id)` for the renderer's caches `0x8189e0` and `0x2c7f300`. Keys and
  hash lookups, never an array index, so a positive id of any size is
  safe. The other `+4` reads after the dereference are floats of a query
  box (`vmovss xmm0,[rsi+4]`). Reads through other accessors (the
  generic `0xadf100`, `0x2d91c0`) were not enumerated: see the proof below,
  which does not need them.
- **Level from id:** only the decoder's loop `0x818b70` (the 14-byte body
  and a looser `lea r,[r*8]` form each occur once). After level 10 its
  step `lea r8d,[r8*8]` wraps to 0, so for every id at or past
  1,227,133,513 it never ends: a stock depth-12 tree would hang the
  renderer, not only mis-number.
- **The skip manager's per-level lists** (`OctreeSkipManager+0x108`, 24-byte
  vectors of node ids): grown, never capped. `0x817870` asks
  `OctreeSystem`'s `0xae2d10` for the level of a size (it loops from the
  configured depth `+0x28` down, `shlx`; no constant) and resizes the list
  to that level plus one (`0x81ae60`). `0x816c70` is the other caller.
- **The depth's readers:** `Resize` (`0xae4c50`, writes it),
  `OctreeSystem::Get` (`0xae2b40`, copies it into the `EcsOctree` it hands
  the starter, asserts `depth > 0`), the starter (`0xae3950`, `[rcx+0x20]`)
  and `0xae2d10`. No other constant 10 or 11 bounds a level in these
  functions.

### Can ids or node order reach the simulation?

- **Ids:** the readers found are the renderer's. The design does not rest
  on that search: a depth-12 deep id is a **pure function of the node's
  cell**, as a stock id is a pure function of the node's path, so two
  games with the same tree have the same ids whoever reads them. A
  counter (tpf2-bigmap's design) would not be: it depends on what the
  process loaded before.
- **Order:** the tree is the game's own: its shape is a function of the
  root box, the depth and the sequence of inserts and moves, which the
  room keeps equal in every game; queries walk children by octant and
  never by id. A different depth gives a different tree and a different
  walk, so **every game of a room on a world past 512 tiles must run the
  same setting** (12); on worlds of 512 tiles or less, setting 12 behaves
  as 11, and on 256 or less as the stock game. The room does not check the
  setting yet (§7).

### The design (TF3's, cheaper than TF2's)

- Root: past 512 tiles, the root splices call `Resize` with depth 12 and
  ±131,072 m (1,024 tiles); 257 to 512 tiles keep depth 11.
- Deep ids: level 11 (the leaves, 128 m cells) gets `0x50000000 + zslot·2²²
  + y·2¹¹ + x`, from the tight box the descent receives (`[rsp+0x48]` at
  entry) and the root box in the `EcsOctree` (`+8`): x and y the cell in
  the 2,048 by 2,048 grid, zslot one of 128 height slots from −8,192 to
  +8,192 m. Ids run `0x50000000` to `0x6fffffff`, past every stock id
  (`0x49249248`). A node outside the height band is clamped (logged once);
  its id may then repeat, which only the renderer's caches see. Levels 0
  to 10 keep the game's ids. Level 11 is the leaf level, so no id is
  derived from a deep one.
- Decoder: a splice before the loop (`0x818b5b`, `mov r12d,r9d; cmp
  edx,r8d`): an id at or past `0x50000000` sets `r9d = 11` and `r8d =
  0x7fffffff`, so the stolen instructions give level 11 and `jl` skips the
  loop. Stock ids run the loop as before.
- Install order: the decoder splice and the descent detour (both
  pass-through on any tree shallower than 12, since the descent reads the
  depth from its own `EcsOctree`), then the root splices; any failure
  leaves nothing installed.

### Run offline on the game's own code

`depth12.rs`'s tests relocate the descent (1,421 bytes), its starter and
the decoder from the executable, answer the ECS calls with a model of the
component store, and insert 3,000 objects over a 1000 x 186 map:

- unpatched at depth 12, over 1,000 level-11 ids are ones the stock
  decoder never ends on;
- patched at depth 11: the same tree and ids as unpatched, and the patched
  decoder gives every stock id its stock level;
- patched at depth 12: every id positive and unique, levels 0 to 11 only,
  loose boxes `2 × 262,144 / 2^level`, 128 m cells at level 11, every deep
  id the function of its cell, every node's level read back right by the
  relocated decoder with the splice;
- the same objects inserted in reverse order after other worlds give every
  node box the same id;
- a target moved by a byte installs nothing.

`octree.rs`'s tests run both root sites with `Resize`: set to 12, 176 tiles
keep depth 10, 300 and 512 get 11, 1,000 and 1,024 get 12, 1,026 keeps the
game's.

### Shapes and memory

`crates/tpf3mp-bigmap/tpf3mp_bigmap.stage4.toml`: rows 128 to 408 tiles

environment: `TPF3MP_BIGMAP_OCTREE=12`, `TPF3MP_BIGMAP_STREET_RASTER=1`,

- `big maps: octree: bigmap::octree_root_init: a world of 100 x 1000 tiles; root at depth 12, ±131072 m`

  from `0x50000000` to `0x6fffffff`)
